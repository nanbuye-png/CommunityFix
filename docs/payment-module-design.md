# 报修计费与支付模块设计草案

2026-11-04更新：用户已确认先做模拟支付、报价确认后维修、验收后付款，追加费用再次确认。第一期实施范围与使用说明见[payment-phase1.md](payment-phase1.md)，下文保留原始设计讨论，不再表示这两项待确认。

2026-11-03。根据用户提出的公共设施不向报修居民收费、住户自有设施维修由住户支付的规则拟定。本文是需求草案，尚未新增数据库、改动收费流程或接入支付渠道。交互验收暂缓，正式环境不部署。

## 已确定的业务原则

- 楼道、电梯等公共设施维修不向报修居民收费；居民家中自有设施维修支持自费。
- 设施归属与维修分类分开。水管、灯具等类别不能直接决定收费；发生在家中的公共管线也不能仅凭位置判断为居民自费。
- 当前系统没有报价、账单或支付模块，报修必须选择已绑定房屋。公共设施需独立表达所在小区、楼栋及位置，不把居民房号冒充故障位置。

## 建议第一期流程（待确认）

公共设施：居民提交公共位置 → 物业核实归属 → 派单维修 → 居民验收。显示“居民无需支付”，不创建零元支付交易。

自有设施：居民提交 → 物业核实归属并报价 → 居民确认报价 → 维修 → 居民验收 → 支付账单。增加费用必须重新报价并由居民确认；不能让客户端提交金额覆盖账单金额。具体付款时点尚待用户确认，不能据此开始实施付款条件。

归属或责任不清时由物业核实，不由AI自动收费。免收、保修等后续例外需要独立原因和审计，不能擅自将公共设施改成向居民收费。紧急险情的抢修与付款约束需明确应急例外。

## 业务数据与状态建议

| 对象 | 主要职责 |
| --- | --- |
| 报修位置与设施归属 | 区分公共设施与自有设施，记录位置、物业确认与变更依据 |
| 报价及明细 | 人工、材料等明细，金额、版本、报价人、居民接受或拒绝记录 |
| 账单 | 关联已确认报价、付款人、收款方、应付金额与币种，免付、待付、已付、关闭等独立状态 |
| 支付交易 | 每次渠道下单、商户订单号、渠道交易号、状态、支付时间；失败或超时可以重试而不重复计费 |
| 退款记录 | 原交易、退款金额、原因、审批和渠道结果；累计退款不能超过已收金额 |
| 回调及对账记录 | 验签、去重、异常定位、主动查单与账单核对 |

金额在服务端使用人民币“分”的整数存储和计算；前端只展示金额，不决定最终收费。支付状态独立于维修状态：已完成维修可以同时处于待支付，评价、返修、投诉规则需明确，不直接借用 CLOSED 表示结清。

历史工单不自动生成欠费。新规则应从明确的启用版本或时间开始；历史数据保持原有行为。

## 角色分工建议

- 居民：查看自己报修的报价、确认或拒绝报价、支付本人账单、查看交易与退款进度。
- 物业：仅在授权小区确认归属和报价、查看账单并处理收费争议与退款申请。
- 维修工：查看执行所需的报价项目，提交实际用料或追加费用申请，不能直接修改已确认金额或标记支付成功。
- 系统管理员：配置支付渠道、查看必要的平台交易运维与审计信息；不因管理员身份自动开放全部居民报修正文和收件箱。

收款主体与是否向维修工结算尚未确定。第一期建议单一明确收款方，不默认加入钱包、余额、提现、多方分账或平台资金托管。

## 技术接入建议

在现有后端增加边界清楚的计费/支付业务模块与支付渠道接口，保持未来拆分独立服务的能力；是否立即拆成独立Spring Cloud服务暂不预设。模拟渠道与真实渠道明确区分，模拟成功不构成真实收款。

支付成功必须由服务端验证可信渠道结果，并核对订单、金额、币种、收款商户等信息；前端页面跳转或客户端回传成功不能直接结清账单。重复回调、重复点击、关闭订单后晚到的成功通知必须有明确处理规则。具体验签与渠道协议在选择真实渠道后按其官方文档实现。

MySQL事务、唯一约束与幂等记录承担资金状态一致性。Redis可以辅助限流，不作为是否付款的唯一依据。RabbitMQ可以承接付款结果通知和后续异步任务，使用事务outbox补偿，不能仅因消息ACK而认定付款成功。WebSocket用于提示报价或账单变化，最终状态通过鉴权HTTP接口查询。
