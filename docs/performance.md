# 本地隔离性能验收

本轮新增 `deploy/acceptance.py performance`，使用独立 Compose 项目，经 Nginx/Gateway/两个业务实例执行同样的 10 万工单、100 用户、120 秒预热、600 秒采样。实际结果、首次统计接口超标及修复复测见 [本轮报告](local-acceptance-results.md)，复现及清理见 [运行指南](local-acceptance.md)。下文直连单实例结果保留为历史记录。

## 运行方法

在 CommunityFix 根目录先重新打包业务服务，再运行：

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File deploy/run-backend.ps1 -Package
python deploy/performance-local.py
```

前置条件：Java 21、Python 3.12、Docker Desktop，以及已健康运行并映射 `127.0.0.1:3307` 的 `communityfix-mysql-1`。脚本拒绝使用比源文件旧的业务 jar；不读取 `deploy/.env`，不使用真实 AI 或微信凭据。不要在正式数据库服务器执行负载测试。

脚本只创建随机名称的 `cf_perf_*` 库和仅授权该库的随机账号。Flyway 在空库迁移，生成演示基础数据后增加 100 个独立测试账号、10 万张合成工单，启动独立后端 `127.0.0.1:18080`。完成或异常退出时停止其 Java 进程并删除临时库、账号，原业务库不作为写入目标。

默认参数为 100 用户、120 秒预热、600 秒正式采样，每个用户一次只发送一个请求，请求间隔 0.2 秒。首次登录在负载开始前完成，登录耗时不计入普通登录后接口指标。短测命令：

```powershell
python deploy/performance-local.py --warmup 15 --duration 45
```

无需 Docker 的保护逻辑检查：`python -B deploy/test-performance-local.py`，覆盖无效参数、占用端口、授权失败后的库/账号清理，以及监测失败时及时停止工作线程。

## 数据和负载口径

80% 虚拟用户是居民，20% 是物业管理员，全部使用独立账号和 Token；物业账号授权同一个合成小区。基础工单 80% 已完成、20% 待审核，创建时间覆盖近 30 天。合成数据不包含历史日志、附件及维修人员任务分布，不能替代全业务数据模型验收。

居民每轮：4 次首页列表、2 次本人详情、1 次通知列表、1 次创建工单、1 次取消刚创建的工单、1 次当前用户查询。物业每轮：5 次首页列表、3 次详情、1 次统计、1 次当前用户查询。取消操作使用创建结果的真实 ID 和版本，每次写入使用独立幂等键。实际比例受各类接口耗时影响，以报告请求计数为准。新增工单仅留在临时库，最终行数会超过初始 10 万。

记录从正式窗口内发起的请求开始到完整读取 JSON 响应的耗时，包括超过窗口结束时间才完成的请求。统计所有响应的 P50/P95/P99、吞吐、HTTP 状态和非预期错误；本场景不故意触发拒绝或冲突，因此所有非 200 都算失败。总体和每类接口均需 P95 < 2000 ms、错误率 < 1%，否则进程返回非零。

每次结果保存在 `.local/performance/<UTC时间-随机后缀>/`：

- `report.json`：配置、jar/源码 SHA-256、MySQL/Flyway 版本、分接口指标、最终行数和清理结果。
- `progress.json`：当前进度与测试库连接数，每约 10 秒更新。
- `backend.log`：隔离后端的本地运行日志。
- `runner.py`：本次运行脚本快照，可与报告中的 `runnerSha256` 核对。

原始报告目录被 Git 忽略；正式证据可复制到 `docs/evidence/`。报告不包含账号密码、Token、供应商密钥或原业务数据。连接数来自 MySQL `information_schema.processlist` 中测试库连接数采样，不是整个 Docker MySQL 的总连接数。

## 验收范围

需求规定的是 4 核、8 GB 服务器；当前本机环境的结果只能说明本机回归表现。此脚本直连单个业务服务，未覆盖 Gateway/Eureka、HTTPS、MinIO、真实网络、图片上传、AI、维修容量争用、深分页、模糊搜索或持续增长的历史表。完整时长通过仍需在规定服务器和最终部署拓扑复测。

## 2026-10-19 短测

本机为 Windows 11，32 个逻辑处理器、15.69 GiB 物理内存；Docker 分配 32 CPU、8,155,529,216 字节内存。MySQL 8.4.5、Flyway V1～V4；Java 堆为 256 MiB～1 GiB，Hikari 上限 10 个连接。没有将整套服务约束为规定的 4 核、8 GB。

15 秒预热、45 秒采样：初始 100,000 张工单、100 个用户；6,351 次请求均返回 200，总体 P50/P95/P99 为 430.88/1179.41/1486.94 ms，吞吐 141.13 请求/秒。各接口 P95 也均低于 2 秒。最终 100,658 张工单，连接数采样均为 10，临时库和账号已删除。

[短测原始报告](evidence/performance-2026-10-19-short.json)。短测用于确认场景可执行，不等于完整时长验收。

## 2026-10-19 完整时长本机回归

命令：`python deploy/performance-local.py`。120 秒预热、600 秒正式采样，初始 100,000 张工单、100 个独立用户。共 88,409 次请求，全部成功，总体 P50/P95/P99 为 422.43/1038.90/1356.90 ms，吞吐 147.35 请求/秒，非预期错误率为 0。

采样窗口开始前会创建/取消预热工单，因此正式窗口内取消数与创建数不必相等；窗口结束时可能保留尚未取消的合成工单。它们随整个临时库一起删除。最终工单数 109,124，连接数 71 次采样均为 10；临时库、账号和独立 Java 进程均已清理。

结果为本机普通接口场景 PASS，总体和每类接口均满足 P95 < 2 秒、错误率 < 1%。不代表 4 核、8 GB 规定服务器或最终 Gateway/HTTPS/MinIO 部署验收。统计接口余量最小，后续在规定服务器复测时重点观察。
